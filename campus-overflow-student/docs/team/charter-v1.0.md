## 1. 团队价值观

1. **对事不对人**：评审、回顾只讨论代码与过程，不针对个人。
2. **透明第一**：遇到阻塞、延期、不懂立即同步，不隐瞒、不拖到最后。
3. **承诺即履行**：Sprint 中认领的任务，除非有无法控制的障碍，否则必须完成到 DoD。
4. **小步快跑**：少做大而全，多做可评审、可演示的增量。
5. **共同成长**：互帮互助，愿意 review 他人代码，也乐于被 review。

| 场景 | 约定 |

## 3. 开发规约（分支 / 提交 / PR）

### 3.1 分支策略
- `main` 为受保护分支，**禁止直接推送**，只允许通过 PR 合并。
- 新功能分支命名：`feature/<功能名>`；修复：`fix/<bug名>`；紧急修复：`hotfix/<名>`。
- 每个任务从 `main` 切独立分支，开发完成后合并即删。

### 3.2 提交规范
- 使用前缀约定：`feat:`（新功能）、`fix:`（修复）、`docs:`（文档）、`refactor:`（重构）、`test:`（测试）、`chore:`（杂项）。
- 提交信息用祈使句描述做了什么，如 `feat: 实现提问接口`。

### 3.3 PR 规范
- 每个 PR 关联看板任务，标题清晰，描述包含：改了什么 / 为什么 / 如何验证。
- 至少 1 名成员 review 且回复 **LGTM** 后方可合并；`main` 分支保护强制该规则。
- 合并操作由 **SM**（或 PO 授权的成员）执行。

### 3.4 代码规范
- 后端：Java 21 + Spring Boot 3 + Maven，遵循 DDD 分层（domain/application/infrastructure/interfaces）。
- 前端：React 18 + TypeScript 5（strict 模式，禁 `any`）。
- 所有新代码必须先写单元测试；覆盖率目标：领域层 ≥ 90%，整体 ≥ 70%。

## 4. 完成的定义 DoD（Definition of Done，初版）

一个功能**只有同时满足以下全部条件**才算"完成"：

- [ ] 代码已实现并通过本地/CI 单元测试（`mvn test` / `pnpm test` 全绿）
- [ ] 已通过代码评审，PR 获得 LGTM 并合并到 `main`
- [ ] 已接入数据库/接口，端到端调用可验证
- [ ] 关键业务规则有对应测试覆盖，无"无效断言"
- [ ] 无编译警告、无 `TODO` 遗留、无硬编码敏感信息
- [ ] 已更新必要文档（如 ADR、接口说明）
- [ ] 看板任务卡片移入 Done 列

> DoD 为初版，随项目推进可在回顾会修订。

## 6. 风险与障碍处理

- 风险统一登记在看板/文档，SM 负责跟踪闭环。
- 常见障碍（环境配置、依赖冲突、接口不通）优先团队内部解决，超时未决 SM 上报教师。
- 每周 SM 主动巡检一次：分支是否规范、PR 是否积压、DoD 是否落实。
