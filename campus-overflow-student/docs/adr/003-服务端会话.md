# ADR-003：认证采用 Redis 服务端会话而非 JWT

**状态**：已接受 ｜ **驱动特征**：安全性、可运维性 ｜ **相关场景**：登录/登出、CSRF 防护

## 背景

前端是独立部署的 SPA，后端提供 REST 接口。认证方案需要在「用户主动登出后立即失效」「多标签页状态一致」
「防 CSRF」三件事上都能给出确定答案。纯 JWT 方案是无状态的，但令牌一旦签发就在有效期内始终有效，
要做到「登出即失效」或「改密后踢下线」，反而必须再引入一份黑名单存储，等于把状态又搬回来。

## 决策

1. **会话状态放在服务端 Redis**：引入 Spring Session（`spring.session.store-type=redis`），
   命名空间 `co:session`，会话超时 30 分钟（`spring.session.timeout=30m`）。
   Redis 连接超时 2s，随 `docker compose` 一起提供。
2. **会话标识用 HttpOnly Cookie 传递**：Cookie 名 `SESSION`，`http-only=true` 使前端脚本无法读取，
   从而避免 XSS 直接窃取会话；`same-site=lax` 阻断跨站请求携带；`secure` 由环境变量 `COOKIE_SECURE` 控制，
   `prod` profile 下强制为 `true`。
3. **CSRF 用双提交 Cookie**：`CookieCsrfTokenRepository.withHttpOnlyFalse()` 下发 `XSRF-TOKEN`，
   前端从 Cookie 读出后回填到请求头 `X-XSRF-TOKEN`；配合 `SpaCsrfTokenRequestHandler` 与 `CsrfCookieFilter`，
   使 SPA 首次进入即可拿到令牌。校验失败统一返回 `AUTH-403-CSRF` 错误体，提示刷新页面后重试。
4. **认证上下文通过 `HttpSessionSecurityContextRepository` 持久化**，登出即销毁服务端会话，令牌立即失效。

## 后果

- 正面：
  - 登出、改密、管理员踢人都是「删一个 key」，语义确定，无需额外的令牌撤销机制。
  - 会话数据只在 Redis，前端不持有任何可被解析的身份信息，XSS 拿不到可直接使用的凭据。
  - CSRF 完全交给 Spring Security 标准链路处理，不需要前端手写签名逻辑。
- 负面：
  - 认证可用性强依赖 Redis：Redis 不可用时全员无法登录（`docker compose` 已把 Redis 与 MySQL 一起编排，
    并在验收清单中要求两者健康）。
  - 每次请求都要访问一次 Redis 读取会话，比无状态令牌多一次网络往返。
  - 多实例部署必须共享同一 Redis，否则会话不互通——这是课程阶段可接受的约束。

## 被否决的替代方案

- **纯 JWT（无状态）**：省掉 Redis 依赖，但「登出即失效」无法实现；要用黑名单补，等于又引入服务端状态，
  复杂度反而高于直接使用会话。
- **容器内默认的 HttpSession（Tomcat 内存）**：零配置，但进程重启即全员掉线，多实例无法共享，
  且无法在容器滚动重启时保持登录态。
