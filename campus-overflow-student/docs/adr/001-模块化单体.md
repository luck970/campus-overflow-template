# ADR-001：采用模块化单体 + 六边形分层

**状态**：已接受 ｜ **驱动特征**：可测试性、可演进性、团队协作 ｜ **相关场景**：FF-1、FF-2、FF-3

## 背景

CampusOverflow 是一个课程规模的校园问答系统，需要在 5 人团队、多个 Sprint 内持续交付。
我们既希望获得 DDD 限界上下文带来的清晰边界（便于 3 名开发者并行开发、互不踩脚），
又不希望在课程阶段承担微服务带来的分布式复杂度（服务拆分、网络调用、分布式事务、独立部署运维）。
同时，领域逻辑必须可在毫秒级完成单元测试，不被 Spring、JPA 等框架绑架。

## 决策

1. **部署形态采用模块化单体（Modular Monolith）**：整个系统作为一个 Spring Boot 应用部署，
   但内部按限界上下文严格拆分为多个 Maven 模块，模块间只通过显式的 API 依赖协作。
2. **顶层模块按限界上下文划分**：
   - `co-shared-kernel`：共享内核（统一异常、分页、Actor、事件基类等）。
   - `co-identity`：身份与访问（用户、课程、角色、会话）。
   - `co-qa`：问答核心（问题、回答、投票、评论、标签）。
   - `co-reputation`：声誉与成就（积分、徽章、账本）。
   - `co-discovery`：发现与搜索（全文检索、标签、通知、@提及）。
   - `co-bootstrap`：启动与装配（主类、配置、安全、全局异常、发件箱中继）。
3. **每个上下文模块内部再按六边形（端口与适配器）分层为子模块**：
   - `co-xxx-api`：对外发布语言（DTO、集成事件、开放主机服务接口）。
   - `co-xxx-domain`：领域层（聚合、实体、值对象、领域服务、仓储端口），纯 Java、零框架依赖。
   - `co-xxx-application`：应用层（用例编排、命令/查询、出站端口接口、事务边界）。
   - `co-xxx-infrastructure`：基础设施适配器（JPA 实体、仓储适配器、读模型、缓存、Flyway 脚本）。
   - `co-xxx-interfaces`：入站适配器（REST Controller、请求/响应模型）。
4. **依赖方向只能由外向内**：`interfaces → application → domain`，`infrastructure → application/domain`；
   `domain` 不依赖任何外层与框架。跨上下文只允许依赖对方的 `api` 子模块，禁止直接访问其领域或数据表
   （由 ArchUnit 规则 FF-2 守护）。

## 后果

- 正面：
  - 边界清晰，3 名开发者可分别认领不同上下文/模块并行开发，合并冲突少。
  - 领域层毫秒级、无容器单元测试；更换持久化或 Web 框架只影响对应适配器。
  - 单体部署运维简单，没有分布式事务；未来若某上下文需要独立，可沿模块边界平滑抽取为服务。
- 负面：
  - 模块与子模块数量多，工程结构和 POM 配置有一定样板成本。
  - 需要团队自律并依赖 ArchUnit 守护，防止模块边界被“走捷径”破坏。

## 被否决的替代方案

- **无分层的单一 Web 工程（按技术包分层）**：写起来最快，但业务边界被技术分层淹没，
  3 人并行时频繁冲突，领域逻辑与框架耦合，无法满足可测试性与可演进性目标。
- **从一开始就拆成微服务**：能获得独立部署能力，但课程规模下分布式通信、数据一致性、
  运维成本远超收益，且会让团队把精力从领域建模转移到基础设施上。
- **每个上下文一个独立数据库 Schema 但仍共享代码**：物理隔离过度且在单体下增加配置复杂度，
  模块化单体 + 逻辑边界已能满足当前协作与演进需求。
