# ADR-005：搜索使用 MySQL ngram 全文索引

**状态**：已接受（可演进） ｜ **驱动特征**：可演进性、部署简单 ｜ **相关场景**：问题检索、搜索投影

## 背景

问答系统的核心检索场景是中文标题与正文的子串匹配。中文没有空格分词，`LIKE '%关键词%'` 无法利用 B+ 树索引，
数据量上来后是全表扫描；同时搜索属于 `co-discovery` 上下文的读侧能力，不应该让 `co-qa` 的写入路径依赖搜索引擎。

## 决策

1. **检索能力定义为端口**：`co-discovery-domain` 提供 `SearchPort` 与 `SearchQuery`，领域层不感知具体存储。
   `co-discovery-infrastructure` 提供两个适配器：
   - `MySqlFullTextSearchAdapter`：默认实现，使用 MySQL InnoDB 全文索引；
   - `LikeSearchAdapter`：退化实现，用于对照与降级。
   由配置 `co.discovery.search.engine: fulltext | like` 切换，默认 `fulltext`。
2. **索引使用 ngram 解析器**：建表脚本中 `FULLTEXT KEY ft_doc (title, body_text) WITH PARSER ngram`，
   依赖 MySQL 内置 ngram 分词（默认 `ngram_token_size=2`），从而支持中文两字词及以上的子串检索。
3. **搜索数据独立于写入模型**：检索表由 `co-discovery` 自己的 Flyway 脚本创建，通过领域事件投影维护，
   不直接 join 问答上下文的表。

## 后果

- 正面：
  - 不引入额外中间件，`docker compose` 只起 MySQL + Redis，运维面最小。
  - 中文两字以上关键词可走全文索引，避免全表扫描；`MATCH ... AGAINST` 天然带相关性排序。
  - 端口与适配器结构使未来换 Elasticsearch 只影响 `infrastructure` 一个模块。
- 负面：
  - ngram 分词的停用词表会把「包含停用词」的词元整条丢弃（建表脚本注释已写明：默认停用词含 a、i 等，
    会导致含这些字母的英文检索失效），因此英文检索需要额外验证。
  - 相关性打分与查询语法受 MySQL 版本限制，不如专业搜索引擎灵活。
  - `ngram_token_size` 是实例级参数，修改需要重建索引，不能在应用侧热切换。

## 被否决的替代方案

- **`LIKE '%关键词%'` 作为正式方案**：实现成本最低，但无法使用索引，随数据量增长必然退化，
  只保留为 `like` 退化实现用于对照演示。
- **引入 Elasticsearch**：检索能力强，但课程规模下要多维护一个集群与一套同步链路，
  与「模块化单体、最小运维面」的 ADR-001 决策冲突。
