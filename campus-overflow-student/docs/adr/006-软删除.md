# ADR-006：用户内容一律软删除

**状态**：已接受 ｜ **驱动特征**：可追溯性、数据完整性 ｜ **相关场景**：问题/回答删除、声誉与通知引用

## 背景

问答内容一旦被物理删除，会同时破坏三件事：一是审核与申诉失去原始证据；二是声誉账本、通知、
搜索投影中对已删内容的引用会变成悬空引用；三是误删无法恢复。而课程评分本身也要求「内容移除」是
可解释、可追溯的业务动作，而不是一条 `DELETE`。

## 决策

1. **物理表增加删除标记列**：`qa_question`、`qa_answer` 增加 `deleted_at DATETIME(6) NULL`
   （`qa_question.deleted_at` 列注释直接标注「软删除（ADR-006）」），`NULL` 表示未删除。
2. **所有读路径强制过滤**：读模型统一以 `WHERE deleted_at IS NULL` 为基线条件，
   已落地的 `JdbcQaReadModel` 在问题列表、问题详情、回答列表三处查询中均带该条件。
3. **索引与查询模式匹配**：按「过滤 + 排序」的实际访问模式建复合索引，
   如 `idx_question_created (deleted_at, created_at)`、`idx_question_course (course_id, deleted_at, created_at)`、
   `idx_answer_question (question_id, deleted_at)`，保证软删除条件下仍能走索引。
4. **删除动作发布领域事件**：删除后发布 `ContentDeletedEvent`，由下游上下文消费，
   维护搜索投影、通知与声誉视图的一致性，避免各上下文自己去猜内容是否还在。

## 后果

- 正面：
  - 内容可恢复、可审计，教学演示中能完整展示「删除 → 引用方如何响应」的一致性链路。
  - 下游上下文通过事件被动感知删除，不需要跨上下文直接查表，符合 ADR-001 的边界约束。
  - 复合索引把 `deleted_at` 前置，软删除后查询性能不退化。
- 负面：
  - **所有**查询都必须显式带过滤条件，漏写一处就等于把已删内容泄漏给用户，属于高危人为失误点，
    只能靠 review 与测试兜住。
  - 表只增不减，长期需要归档策略（课程阶段不处理）。
  - 唯一约束与软删除共存需要额外设计（例如同一用户重复内容场景），当前通过业务层校验而非数据库唯一键保证。

## 被否决的替代方案

- **物理删除（`DELETE`）**：实现最简单，但不可恢复、破坏审计，且让下游引用悬空。
- **布尔列 `is_deleted`**：能过滤，但丢失「何时删除」这一信息，无法做按时间归档与恢复窗口，
  也无法在多实例并发删除时做幂等判断。
