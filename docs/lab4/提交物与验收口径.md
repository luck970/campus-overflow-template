## 二、「全绿」的判定（决策 D1 落地）

**背景**：`CampusOverflowFlowIT` 断言「提问 → 回答 → 采纳 → 声誉 +15 → 搜索命中 → 收到通知」，后三步依赖 134 个 `TODO(S3)`，本 Sprint 无法转绿；它同时需要 Docker。

**本 Sprint 的构建口径**（写入 `campus-overflow-student/README.md`）：

```bash
# 1) 标准构建口径（验收用）
mvn clean install -DskipITs      # 期望：BUILD SUCCESS，27 模块，55 个单测 0 失败

# 2) 单元测试基线（只增不减）
mvn test                         # 期望：Tests run: 55, Failures: 0, Errors: 0, Skipped: 0

# 3) 集成测试（当前禁用，S3 后恢复）
mvn verify -Dit.test=CampusOverflowFlowIT   # 期望：S3 完成后转绿
```

**口径表述**（对教师）：单元测试全绿；集成测试因依赖 Sprint 3 的搜索、通知、声誉能力而禁用，代码中已写明恢复条件，S3 交付后第一件事即为恢复该测试。**该口径需在 Review 前书面确认**（行动项 A-08）。

## 五、答辩分工与 PO 讲解要点

评分里 30%（结构）+ 25%（不变式）是**理解性得分**，教师随机点名提问属正常。建议每人认领一个切片，并在 Sprint Review 前互相讲一遍：

| 成员 | 讲解切片 | 至少要能回答的问题 |
| --- | --- | --- |
| 唐志烽（PO） | 上下文划分与 ADR 决策链 | 为什么是 4 个上下文 + 共享内核？为什么不做微服务？009 号 ADR 与 002 号的关系？ |
| 左燚之（SM） | 模块边界与架构约束 | 6 条 FF 规则各管什么？跨上下文为什么只能走 `*-api` 或集成事件？ |
| 江思达 | Q&A 全链路 | 一次 `POST /api/v1/questions` 经过哪些层？不变式在哪一行代码被守住？ |
| 何欣怡 | 基础设施与持久化 | 领域对象与 JPA 实体为什么分开？Flyway 为什么按上下文分目录？ |
| 柯博 | 领域不变式与测试 | 42 条不变式里哪些有测试、哪些没有？日志为什么用 JSON 而非文本？ |

**PO 讲解要点（三条，按顺序讲）**

1. **业务驱动划分**：四个上下文对应四类业务能力——身份与课程（谁能提问）、问答（问题怎么流动）、声誉（贡献怎么被激励）、通知与检索（信息怎么找到人）。**不是按技术分层切**，所以每个上下文内部才有 domain / application / infrastructure / interfaces 四层。
2. **决策链**：001 模块化单体（先保证单进程内强一致，微服务的分布式成本在 10 周课程里不划算）→ 002 事务性发件箱（跨上下文只发事件，不共享事务）→ 008 领域与持久化分离（聚合不被 JPA 注解污染）→ 009 包结构（把上述决策落到目录）。
3. **代价与边界**：模块化单体的代价是「约束靠测试而非进程隔离」，所以才有 `ArchitectureTest` 的 6 条 FF 规则；这也是为什么违反分层会在构建期直接失败，而不是靠人工 review 发现。
