1. 事件一律用**过去时 + 业务术语**；"用户操作完成""数据保存"这类抽象事件当场退回。

## 二、分段时间盒与主持动作

### Step 1 · Big Picture（40 分钟）

| 分钟 | SM 动作 |
| --- | --- |
| 0–5 | 讲规则：橙卡 = 领域事件，过去时，业务术语；沿墙从左到右按时间线排，不分组、不论证 |
| 5–25 | 自由贴卡。SM 只做三件事——计时、提示仍在发散的人补卡、把抽象事件当场退回 |
| 25–32 | 全员合并同类卡、排定时间线，标出**系统边界事件**（跨出本系统的"门"） |
| 32–40 | 收口：红笔圈出热点，移到右侧 Hot Spot 区；统计事件数并当场报数 |

**收口信号**：领域事件达到 **30–40 条**即视为充分（本次 38 条，覆盖入校建课→提问→答题→评价→激励→沉淀六段）。不追求穷尽，超时立即停手进 Step 2。

> SM 提醒话术：「现在不是讨论这个事件该不该有，是先把发生过的写下来。」

### Step 2 · Process Modeling（30 分钟）

| 分钟 | SM 动作 |
| --- | --- |
| 0–5 | 说明四色语义：蓝 = 命令、黄 = 角色、粉/绿 = 外部系统、橙 = 已有事件 |
| 5–20 | 逐条事件补命令卡，标注触发角色；**必须把"系统"当角色用**——事件订阅者、策略、投影器、定时任务各是一条命令 |
| 20–25 | 识别外部系统（校园身份、邮件/站内信、定时任务调度），标给对应上下文 |
| 25–30 | 检查每条命令是否都有明确角色和非空前置条件；无人触发的命令标 ❓ 进待确认清单 |

**收口信号**：命令数 **30–35 条**、角色 5–7 类（本次 34 条 / 6 类 / 3 个外部系统）。若命令数远少于事件数，说明有事件没人"下达"，回头补命令，不要跳到 Step 3。

### Step 3 · Software Design 与聚合识别（30 分钟）

| 分钟 | SM 动作 |
| --- | --- |
| 0–5 | 说清定义：**聚合 = 强一致事务边界**；紫卡 = 聚合，卡上写聚合根；读模型不是聚合 |
| 5–18 | 按命令-事件聚类贴紫卡。Developer 主导边界判断，SM 不介入技术裁决，只保证时间 |
| 18–25 | 逐聚合验证不变式并**编号**（I<聚合号>-<序号>），标注违反时的异常码；至少覆盖：采纳唯一、一人一票、悬赏只能结算一次、声誉入账幂等、冻结与可用守恒 |
| 25–30 | 识别读模型（绿），列清单；同时用 `backend/` 模块目录核对每个聚合的物理归属 |

**收口信号**：聚合 **12–15 个**（本次 13 个）、不变式全部编号且有违反行为说明、上下文归属与 Maven 模块一一对得上。若某聚合只有 1 条命令且无不变式，它可能只是实体，退回合并。

### Step 4 · 上下文映射与术语表（20 分钟）

| 分钟 | SM 动作 |
| --- | --- |
| 0–8 | 虚线圈出限界上下文（预期 4 个 + 共享内核），检查是否按业务能力划分；共享内核只留 ID 契约 |
| 8–14 | 标注关系：客户-供应商（U/D）、事件订阅、顺从者、防腐层（ACL）、共享内核；**必须回答"为什么不用伙伴关系"** |
| 14–18 | 术语表定稿：只裁决**一词多义**，重点裁"回答 vs 评论""积分 vs 声誉""已解决 vs 已采纳" |
| 18–20 | 全体过一遍术语表并口头确认签字；拍全景照片（墙面全景 + 每个上下文区域各一张） |

**收口信号**：上下文 4 个 + 共享内核、关系标注齐 5 类、术语 ≥30 条（本次 108 条含代码标识列）。

## 三、现场陷阱与纠偏话术（SM 直接念）

| 触发信号 | SM 话术 |
| --- | --- |
| 出现"用户操作完成""数据保存"类抽象事件 | "这张卡太粗了，业务上到底发生了什么？换成用户能说出口的动作。" |
| 出现"数据库上下文""前端上下文" | "这是技术分层，不是业务边界。按业务能力重新分组——谁负责哪段业务？" |
| 全体只贴了十几个事件就停了 | "声誉和通知那一侧还没人碰。想想用户采纳答案之后，系统里还发生了什么？" |
| 没人写"系统"这个角色 | "用户没点任何按钮，但系统自己做的事，也算一条命令。" |
| PO 或某位 Developer 一人贴了大半卡片 | "剩下的卡由还没贴过的人来写，一人至少两张。" |
| 开始争论某个聚合该不该拆 | "先贴紫卡，边界理由写卡背面。Step 3 只做聚类，不做实现。" |
| 热点区争论超过 5 分钟 | "记下来，进待确认清单，课后找领域专家确认，先往前走。" |
| 时间盒还剩 2 分钟 | "还有 2 分钟收口，只做合并，不再新增卡片。" |

## 四、散场前 5 分钟必做

1. **拍全景照片**：墙面全景一张 + 每个限界上下文虚线区域各一张（课程要求现场照片，缺此项会被判材料不全）。
2. **核对四份素材齐全**：现场照片、聚合清单草稿、上下文边界草图、术语表草稿。
3. **当场报数并记录**：事件数 / 命令数 / 角色数 / 外部系统数 / 聚合数 / 不变式数 / 上下文数 / 术语数，写入纪要第二节，后续所有文档必须引用同一组数字。
4. **明确课后分工**：
   - SM：24 小时内整理文字版落库到 `docs/ddd/`，发起 PR。
   - Developer：复核聚合不变式是否与技术实现一致，补测试缺口。
   - PO：复核术语表与 Backlog 用词一致，裁决 H9 / H10。
5. **记录过程问题**（时间盒是否守住、谁没参与），用于 Lab 6 回顾会。

## 五、主持复盘要点（散会后 SM 自评）

| 维度 | 自评问题 |
| --- | --- |
| 时间盒 | 哪一段超时、超时原因是被技术争论拖住还是被补卡拖住 |
| 参与度 | 是否有成员整段没贴卡；若有，是不知道怎么贴还是被抢话 |
| 规则守门 | 抽象事件退回后有没有真正改写，而不是"先贴上后面再说" |
| 收口质量 | 热点是否都留了结论；留空的必须当天补齐，否则等于没开会 |
| 数字一致 | 纪要、`event-storming.md`、README 三处统计数字是否一致 |
