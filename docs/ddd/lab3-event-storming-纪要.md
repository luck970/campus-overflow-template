## 三、各阶段产出与收口依据

### Step 1｜Big Picture：38 个领域事件

- 按**六段业务主线**排列时间线，每段都有明确起点与终点：

| 阶段 | 业务段 | 事件数 | 编号区间 |
| --- | --- | --- | --- |
| 阶段 1 | 入校与建课 | 8 | #1–#8 |
| 阶段 2 | 提问 | 5 | #9–#13 |
| 阶段 3 | 答题 | 5 | #14–#18 |
| 阶段 4 | 讨论与评价 | 5 | #19–#23 |
| 阶段 5 | 声誉与激励 | 9 | #24–#32 |
| 阶段 6 | 沉淀与发现 | 6 | #33–#38 |

- 命名纪律：**过去时 + 业务术语**，现场退回全部抽象事件（"用户操作完成""数据处理完毕"类），改写后无一保留。
- 集成事件标记：17 条已在 `*-api/event` 包实现为跨上下文集成事件（`event-storming.md` 中带 `**` 者）。
- 系统边界事件单列 3 条：校园身份已核验（入）、邮件/站内信已投递（出）、悬赏已到期（入，由定时任务而非外部回调触发）。

### Step 2｜Process Modeling：34 条命令 / 6 类角色 / 3 个外部系统

- 34 条命令逐条填写「角色 + 命令 + 事件 + 聚合 + 前置条件」，无一条命令缺触发角色。
- 6 类角色：访客、学生、教师、助教、管理员、**系统**（事件订阅者 / 策略 / 投影器 / 定时任务）。系统的引入是本阶段关键决定——服务端自发行为同样是一条命令，否则 Reputation、Notification 等链路会断。
- 外部系统 3 个：校园统一身份（OAuth / 学号目录）、邮件与站内信服务、定时任务调度（Quartz / Spring Scheduler）。定时任务被显式建模为"时间"这一外部触发源，而非藏在聚合里的定时逻辑。

### Step 3｜Software Design：13 个聚合 / 42 条不变式

- 聚类判据：**若两条命令必须同时成立才合法，则落在同一聚合**；否则拆开，用领域事件对齐。
- 13 个聚合按上下文分布：Identity 3（User / Course / CourseMember）、Q&A 5（Question / Answer / Vote / Comment / Tag）、Reputation 4（ReputationAccount / LedgerEntry / Bounty / BadgeAward）、Discovery 1（Notification）。
- 42 条不变式全部**编号化**（I<聚合号>-<序号>），并标注违反时的异常码，可直接转为 Lab 4 单元测试用例。
- 三处关键取舍现场争论最久，均已写入 ADR：Answer 独立聚合（ADR-003 系列）、软删除（ADR-006）、声誉异步 + 账本（ADR-004）。
- 读模型 7 个：课程问题列表、问题详情视图、热门标签、排行榜、搜索索引、相关问题、未读通知计数。**读模型不等于聚合**，现场专门用一句话统一过这个界限。

### Step 4｜上下文映射与术语表

- 限界上下文 **4 个 + 共享内核 1 个**：Identity / Q&A（核心域）/ Reputation / Discovery / Shared Kernel。物理上对应 `co-identity` / `co-qa` / `co-reputation` / `co-discovery` 四个 Maven 模块。
- 标注 5 类关系：客户-供应商（U/D）、事件订阅、顺从者、防腐层（ACL）、共享内核；并显式论证了**为何未采用伙伴关系**（团队规模与发布节奏不满足共同演进成本）。
- 共享内核仅含 `UserId`、`CourseId` 与事件契约，不含业务规则。
- 术语表定稿 **108 条**（要求 ≥30），含代码标识列与 10 条反例清单。

## 四、热点（Hot Spot）裁决记录

现场红卡 10 张，8 张当堂闭环、2 张转入 Sprint Backlog。完整论证见 [`event-storming.md`](event-storming.md) 第四节，此处只留裁决结论。

| # | 热点 | 裁决 | 状态 |
| --- | --- | --- | --- |
| H1 | Answer 是 Question 内部实体还是独立聚合 | **独立聚合**，采纳时显式加载校验归属，仍在 Question 事务内 | ✅ 已决 |
| H2 | 重复采纳如何防止 | **后端强校验**：`acceptedAnswerId != null` 即冲突；前端置灰只是体验 | ✅ 已决 |
| H3 | 问题删除后回答与投票怎么办 | **软删除 + 读模型过滤**，保留审计与声誉依据 | ✅ 已决 |
| H4 | 声誉同步算还是异步算 | **异步 + 只追加账本 + 对账任务兜底** | ✅ 已决 |
| H5 | 撤销投票是否扣回已发声誉 | **按增量结算**，撤销产生负向流水，账本只追加不修改 | ✅ 已决 |
| H6 | 一人一票靠代码还是数据库 | **双保险**：聚合内校验 + DB 唯一键 | ✅ 已决 |
| H7 | 评论是否支持无限层级 | **仅一层二级回复**，父评论不能是回复 | ✅ 已决 |
| H8 | 悬赏积分与声誉是否同一个数 | **两种货币**：声誉只读荣誉值，积分可用于悬赏，冻结/可用分离 | ✅ 已决 |
| H9 | 教师认证（endorse）是否也加声誉分 | 规则手册未覆盖，进 Sprint 3 讨论 | 🕐 待办 |
| H10 | 每日上限按 UTC 自然日，跨时区是否公平 | 进 Sprint 4 复盘 | 🕐 待办 |

**悬而未决的判定纪律**：任一热点争论超过 5 分钟，SM 强制转为红卡进待确认清单，现场只做"能不能往下走"的判断，不做完整技术论证。

## 五、术语定名分歧与裁决

| 分歧词 | 候选说法 | 裁决采用 | 理由 |
| --- | --- | --- | --- |
| 采纳 / 接受 | Accept / Accept Answer | **采纳回答（Accept Answer）** | 与 Backlog US-012 用词一致；"接受"易与 HTTP 语义混淆 |
| 赞 / 踩 | Like / Dislike / Upvote / Downvote | **赞成票 / 反对票（Upvote / Downvote）** | 与 Vote 值对象语义统一，避免与"点赞"混为一谈 |
| 回答 / 评论 | Answer / Comment | **严格二分**：回答可被采纳、计声誉；评论不可 | 二者声誉与权限规则完全不同，绝不可混用 |
| 积分 / 声誉 | Points / Score / Reputation | **积分（Points）用于悬赏，声誉（Reputation）为荣誉值** | 混用会导致冻结额与余额算不清 |
| 已解决 | Resolved / Solved | **已解决问题（Solved Question）** | 与"已采纳回答"状态联动，一个概念只留一个词 |
| 声誉流水 | Entry / Log / Record | **声誉流水（LedgerEntry）** | 只追加语义，禁止叫"日志" |

> 全部 108 条术语与 10 条反例见 [`glossary.md`](glossary.md)。术语变更须走评审，每 Sprint 检查一次。

## 六、现场纠偏记录（SM 主持动作）

| 现象 | 纠偏动作 | 结果 |
| --- | --- | --- |
| 出现抽象事件卡（"用户操作完成""数据保存"） | 当场退回，要求换成用户能说出口的业务动作 | 改写为具体领域事件，退回 __ 张 |
| 出现按技术分层划分上下文（"数据库上下文""前端上下文"） | 立即纠正为按业务能力划分 | 重新分组，收敛为 4 个上下文 |
| 初版把 Course 放在 Discovery、Answer 当 Question 内部实体 | Step 3 交叉核对 `backend/` 代码后修正 | Course 归入 Identity，Answer 升为独立聚合，聚合总数 4 → 13 |
| PO 与个别 Developer 单人贴卡过多 | 要求未贴卡成员补足，每人每段 ≥2 张 | 5 人全部参与 |
| 热点区争论超过 5 分钟 | "记下来，进待确认清单，先往前走" | 10 个热点全部留结论或明确转办 |
